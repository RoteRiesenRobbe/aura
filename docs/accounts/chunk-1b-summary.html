In one sentence

Aura can now tell who you are. Every building block a login needs — password hashing, the rules a password must satisfy, session tokens, the one-time pass that gets a chosen character into the world, the defence against password guessing, and the rule that one account can only be playing once — exists and is tested. None of it is reachable yet: there are no web endpoints, no screens, and no change a player could notice.

What now exists

A new self-contained package, auth, holding six pieces:

Piece What it does
Password hashing Turns a password into something safe to store, using a deliberately slow algorithm so that stealing the database does not hand anyone the passwords.
Credential rules Username length and characters, password length, the requirement for a special character, and a blocklist of the passwords attackers try first.
Session tokens Issues, checks and renews the token that keeps a player logged in — including the counter that makes "log out" actually cancel a session.
Play tickets A one-time, 30-second pass, tied to one specific character, that the game connection presents instead of any password or login token.
Failed-login throttle Slows repeated wrong guesses down, counting both by the address they come from and by the account being guessed at.
Live-session registry Tracks which accounts are currently playing, so one account cannot be in the world twice.

The two rules that shape most of the above

  • A login for a username that does not exist must take exactly as long as one with the wrong password. If it returns faster, anyone can discover which usernames are registered simply by timing the response — and the deliberately vague error message ("incorrect username or password") stops protecting anything. So a login for an unknown account still performs a full, pointless password check against a fixed dummy value. This is built into the password check itself rather than left as a rule the login code has to remember.
  • Logging out has to cancel the token, not just forget it. A session token is self-contained — the server signs it once and afterwards recognises it without looking anything up, which is what makes it cheap. It also means the server has no list of issued tokens and cannot simply revoke one. The counter shipped in chunk 1a solves this: it is stamped into every token and checked on every use, so bumping it kills every token for that account at once. Without it, "log out" would only clear the browser's cookie and do nothing about a copy taken off the machine.

Three smaller details worth knowing

  • There is no account lockout, on purpose. Repeated wrong guesses get slower and slower, up to a 30-second delay, but the account is never locked. A hard lockout would let anyone who knows your username lock you out deliberately — a defence that turns into a griefing tool, which the game's design principles rule out.
  • The play ticket cannot be pointed at the wrong character. The character's identity comes out of the ticket, and the game connection carries no character field at all — so "a ticket for character A cannot be used to play character B" is not a check that could be forgotten. There is nowhere to say B.
  • The password blocklist is checked after stripping trailing punctuation. Requiring a special character pushes real people towards password!, which would otherwise sail straight through a check that password would have failed — the rule intended to strengthen passwords quietly defeating the rule that does the real work.

What this chunk deliberately does not do

  • No web endpoints. Nothing can be logged into yet. The eight endpoints are chunk 1c.
  • No screens. Character select, login and register forms are chunk 2.
  • No connection to the game world. Getting a chosen character into the world is chunk 3.
  • No password recovery. That is its own plan, sequenced last, because it is the only part of accounts that needs outbound email — which the project has no capability for at all.
  • No player-facing change whatsoever. The game plays exactly as it did yesterday.

The distinguishing feature of this chunk: the tests were proven able to fail

A test that has never failed proves nothing. Every load-bearing rule above was verified by deliberately breaking the code underneath it and confirming the test went red — then putting the code back. Eight such runs, all caught:

What was broken What noticed
Let an unknown username skip the pointless password check The timing test — 0 seconds against 0.26 seconds
Check the blocklist without stripping trailing punctuation Six rows of the password table, password! first
Skip the session-cancellation check Both the revoked-token test and the renewal-refusal test
Trust a token's own claim about how it was signed The forged-token test
Check "is this account already playing?" separately from claiming the slot The concurrency test — two sessions granted where one is allowed
Let a play ticket be used more than once The single-use test
Remove the limit on simultaneous password hashing The concurrency-bound test, at every setting
Drop one early check in that limit The refusal test — but only 2 runs in 5, see below

One of those runs corrected a wrong belief

Removing the check that pins how a token was signed left one kind of forgery still rejected and let another straight through. The two were being treated as one protection; they are not. The test now says so explicitly, so nobody later concludes the check is redundant because one of the two tests still passes without it.

One of those runs found a real defect

The limit on simultaneous password hashing originally decided between "a slot is free" and "the requester has given up" by asking both at once — and when both are true, the language picks at random. So a request whose sender had already disconnected still consumed a full password hash about half the time, which is precisely the work the limit exists to avoid. It now checks the requester first. The mutation run above is what proved the difference is a coin flip rather than a theoretical concern.

Two architecture questions raised during the work, and their answers

1. "Will logins slow the game down when many people sign in?"

A fair concern: password hashing is deliberately expensive, and it happens inside the same program that runs the game. The answer, measured rather than assumed:

  • The game loop is a single thread, so it can never use more than one of the server's two processor cores however busy it gets. Web requests run separately and share no locks with it, so a password hash can never freeze the game — only compete with it for processing time.
  • At an idle or moderately busy server there is spare capacity and a hash is close to free. At the server's measured breaking point there is not — roughly half a core is genuinely spare, so a hash competes and both slow down. An earlier version of this analysis claimed a hash was simply "free"; that was too strong and has been corrected.
  • What was genuinely unbounded was how many at once. The guessing throttle limits each address and each account but never the total, so many different sources could each demand one hash simultaneously. A limit on concurrent hashing was added.

Moving login to a second program on the same server would not have helped — the processor is shared either way, and the operating system divides time between programs exactly as it does within one. It would have added complexity for no isolation.

2. "What about 100 concurrent players, permanently?"

At that scale logins are not the constraint — the game loop is, and it is already measured to struggle there. Load tests against the live server show a comfortable full frame rate with 120+ players spread across the world, but a ceiling of roughly 60–70 when everyone is clustered in one place and fighting. Logins at 100 concurrent players work out to about 2.5% of one processor core.

Two properties keep it that cheap, and both could be removed by accident later, so they are now recorded in the code:

  • Reconnecting costs no password hashing at all. A returning player presents their existing session token, which is checked in microseconds. So the rush of everyone reconnecting after a server restart is cheap.
  • Players who have not registered never reach password hashing either, because an anonymous account is identified by a fast lookup key rather than a password. Since the design is anonymous-first, most players never touch the expensive path.

The things that would actually need to change for a sustained 100 players are all in the game loop, not in accounts — and the cheapest of them, a server with a faster single core, happens to improve both problems at once.

Two proposals considered and not taken

A separate database for accounts and login

Rejected, for reasons specific to this design rather than general ones:

  • Creating a character and creating an account are one indivisible act here. Because players start anonymously, a new player's very first character creation writes the account, its credentials and the character together, all-or-nothing. That is the most common write in the whole product, and it is deliberate — it is what makes signing up later cost no progress. A database boundary runs straight through the middle of it.
  • The link between an account and its characters could no longer be enforced. Databases cannot enforce that relationship across a boundary, so "this character belongs to a real account" would become ordinary code that can be got wrong — exactly the kind of rule this project has been pushing into the database.
  • Backups would double and gain a new requirement: both databases would have to be restored to the same instant, or characters end up pointing at accounts that do not exist. A single backup gives that for free.

The separation actually wanted already exists one level down: login material lives in its own table precisely so ordinary game queries can never read it. The decisive point is that a split database's costs are ongoing, not one-time — doing it early only saves the cheap part, while the expensive part is paid forever.

An abstraction layer for "auth might move elsewhere one day"

Also not taken, but the goal behind it was addressed — see below.

Keeping the door open: three rules for chunk 1c

Moving login to a separate machine later should stay a deployment decision rather than a rewrite. That is largely already true, mostly as a side effect of the play-ticket design. Three rules preserve it, all free today and expensive to retrofit:

  1. The game server never sees a credential. No password and no login token ever reaches it — it receives a ticket and exchanges it for an account and a character. Already true.
  2. The ticket stays opaque to everyone but the auth code. Nothing else reads inside it. This keeps a future change of ticket format contained to one file instead of rippling through the network protocol, the browser client and the test harness.
  3. Web request handlers never reach into the running game. They talk to the database layer and the auth package only — which is verifiably true today, since neither of those packages depends on any game code at all.

One known exception is recorded rather than designed around: logging out is meant to end a live game session, which does reach into the running game. If the split ever happens, that becomes either a small internal call or an accepted gap.

Decisions taken during the work

Decision Outcome
How slow password hashing should be One step above the library's default, chosen by measuring rather than by convention: the usual recommendation measured at over half a second here, which is already noticeable when logging in. The live server is roughly three times slower than the development machine, so this should be measured there and re-chosen while the server is being set up.
How many passwords may be hashed at once Two. A stricter limit of one would protect the game loop slightly better; two was chosen for tolerance of a burst of simultaneous logins. Both alternatives and their trade-off are written down at the setting itself.
Whether this chunk touches the database at all Two queries only — reading and bumping the session-cancellation counter. Without them, "a token belonging to a deleted account is refused" would be a claim nobody could test.
Where the live-session tracking belongs Built here as a standalone, tested component; connected to the running game in chunk 3, where the join path and reconnection handling already live. This was an open question left by the previous session and is now settled in writing.
What characters a character name may contain Deliberately left open. Length, surrounding spaces, invisible characters and the reserved test-harness prefix are all enforced; which letters and symbols are allowed is not, because no plan decides it and quietly inventing a rule would be a design decision in disguise. Flagged for chunk 1c.

Verification

  • The full backend test suite passes — 30 of 30 packages (29 plus the new one), both with and without a test database available.
  • The new tests run twice back-to-back, to prove they leave nothing behind.
  • Eight deliberate breakages, all caught — the table above.
  • The server was started for real with a database configured: it reported zero errors and zero warnings, with all content loading exactly as before — 64 mobs, 86 skills, 15 factions, 4 quests, 777 props, 485 spawns.
  • No browser test applies to this chunk: no game code, no content and no network protocol changed, so nothing the existing 17 browser scripts check could have moved.

One environment note: the tool that detects certain concurrency bugs automatically cannot run on this development machine, as it requires a C compiler that is not installed. The affected test was written to detect the problem by counting outcomes instead, and was confirmed to catch it that way.

What comes next

Chunk Scope
1c The eight web endpoints: create / list / delete / choose a character, and register / log in / log out / refresh. Also tightens two permissive settings that are harmless today but become security holes the moment a login exists, and makes a missing database configuration stop the server rather than warn.
2 The screens players actually use — character select, character creation, login and register forms.
3 Connecting a chosen character to the running game world, and enforcing one live session per account for real. Shipped alone this means: you log in, pick your character, and enter the world as that character — but progress does not yet survive.
4 Saving and loading — the part persistence is actually for. Level, experience, skills, equipped slots and quest progress surviving a restart. ⚑ Added on 1 August 2026 after a review found it fully designed but assigned to no chunk at all.

⚑ Between chunks 3 and 4 there is a window where the account persists and the progress does not: create a character, level it, come back, and it is level 1 again with the right name. That is not worse than today — restarts already wipe everything — but it will look like a bug to anyone testing, so 4 should follow 3 promptly.

One item is deliberately left dangling for 1c and recorded so it is not rediscovered: the signing key for session tokens is read by nothing yet. The name is defined and the strength of the key is validated, but no part of the running program reaches for it, because this chunk has nothing to sign anything for.
