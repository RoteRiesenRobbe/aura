Step 8a, Chunk 1a: the database foundation

Point-in-time summary · 31 July 2026 · branch accounts-8a

This is a human-facing snapshot, not a maintained document. The authoritative sources are docs/archive/plan-accounts-schema.md (the schema and the reasoning behind every shape), docs/archive/plan-accounts-implementation.md (tech stack, save/load, auth) and docs/archive/plan-accounts-frontend.md §10 (the chunk breakdown). Where this document and those disagree, they win.

In one sentence

Aura now has a database. The full account-and-character schema exists, it is created automatically when the server starts, and it can be torn back down cleanly — but no part of the game reads from or writes to it yet. That is deliberate: this chunk proves the foundation works before anything is built on top of it.

What now exists

Eight tables, in a dedicated game schema:

Table Holds
accounts The human being. Deliberately tiny — it holds no sensitive data at all.
account_credentials Login material, kept in a separate table so ordinary game queries can never accidentally read a password hash.
characters One life. Name, level, experience, which slot it occupies, and its link to the character it succeeded.
bloodline_unlocks Rewards earned by sacrificing a character, which outlive that character.
character_spellbook Which skills a character knows, and at what level.
character_loadout_slots What is equipped in each aura / passive / cooldown slot.
character_flags Quest progress and NPC state — the live quest ledger's permanent home.
audit_log Successful account events (logins, registrations, erasures) for support purposes. Failed logins are deliberately absent — an attacker can generate those at will.

Alongside them: a connection layer that talks to Postgres, and the machinery that keeps the schema in step with the code.

Three details worth knowing

  • The "one alive character per slot" rule is enforced by the database itself, not by application code remembering to count first. A second living character can simply never be created in an occupied slot, and a slot frees up the moment its occupant is sacrificed or deleted. This is why the tests need a real Postgres rather than a mock — the invariant is the database.
  • The session-revocation counter shipped now, not later. It is what makes "log out" actually mean something — without it, logging out only clears the browser's cookie and does nothing about a token copied off the machine. Everything built later that needs to cancel a session depends on it existing first.
  • Nothing is ever hard-deleted. There are no cascading deletes anywhere, on purpose: a graveyard that can be silently broken by a stray delete is worse than one that refuses to be broken. Characters are soft-deleted; accounts are anonymised.

How it runs

The schema is created and updated automatically when the server starts, rather than as a separate manual step during deployment. Two reasons:

  • It is one less thing to forget during a deploy.
  • It makes it impossible for the running code and the database to disagree about what the schema looks like.

The schema definitions are baked into the server binary itself, so the deploy stays what it has always been — copy one file across, restart it. No database tooling needs to be installed on the server.

What this chunk deliberately does not do

  • No game code touches the database. No saving, no loading, no logins.
  • No player-facing change whatsoever. The game plays exactly as it did yesterday.
  • The server still starts fine without a database configured — it prints a warning and carries on. This keeps every existing test script and local setup working. That will be tightened to a hard requirement in chunk 1c, once there is actually something to log into; a database that is configured but unreachable already stops the server.
  • The "home campfire" column ships empty by design. Nothing writes it yet, and nothing needs to — characters spawn exactly where they do today.

Running it locally

Three environment variables are needed, all set once by hand and documented in plan-accounts-implementation.md §0: a connection string for the working database, one for a disposable test database, and a signing key. Without them, the server runs without persistence and the database tests skip — which is intentional, so nobody is forced to install Postgres to work on the game.

  • go test ./pkg/aura/store/... — the schema tests. They roll the test database all the way down and back up, so point them only at the disposable one.
  • go test ./... — the full suite; passes with or without a database present.

One trap worth knowing before you set this up: Postgres' own command-line tool is more forgiving about passwords than Go is. A connection string that works perfectly by hand can be rejected outright by the server if the password contains characters like ^, > or a space. Percent-encode it — the setup instructions carry a one-liner that does this safely.

Decisions taken during the work

Decision Outcome
Which database libraries, and at what version Slightly older, pinned versions — so the project's minimum Go version does not have to move. They were tested against the actual Postgres 18.4 server before being adopted, so "older" does not mean "unproven". The pins are explained in the implementation plan; one of them exists purely to stop the dependency tooling raising the language version behind our backs.
What happens when no database is configured Warn and continue, for now. Flipping this to a hard failure is explicitly assigned to chunk 1c and flagged in the code where the decision lives.
One schema file or several One. These tables are created together and no subset of them is meaningful alone.

Problems found and fixed

Three genuine defects surfaced during the work. All three are fixed, and the two in our own code were each demonstrated failing before the fix was applied — a test that has never failed proves nothing.

1. The database password could leak into the server log

The database library carefully hides the password in its own error messages — but the lower-level error it passes along contains the full connection string in plain text. A single mistyped setting would have written the password straight into the boot log. Connection details are now validated up front and errors never echo the input.

2. A failed schema update would silently jam every future start-up

If a schema change fails part-way, the tooling marks the database as "dirty" and refuses to run again — but the failed change itself has already been undone, so an inspection shows no schema at all. It looks like the update never ran, when in fact it ran and failed. The server now prints exactly what state the database is in and how to recover from it.

This was found the hard way: it happened during the work.

3. A defect in the plan itself, found by re-reading it against the shipped code

The plan described how quest progress should be stored, and it was written before the quest system was actually built. Comparing it against the finished code found it named two pieces of information per quest where the real system has three.

Today the missing third piece happens to be redundant — but only because no quest is yet marked repeatable. The moment one is, the omission would silently lose a player's in-progress quest run, and the cause would show up in content long after the code that caused it. The plan has been corrected.

Pre-existing issues noticed (not caused by this work, not fixed)

  • Mob content is excluded from version control in the folder that gets baked into the server binary — uniquely among all eight content types, which are all tracked normally. The practical effect: a fresh copy of the project cannot run its tests green until someone does a build first. This machine's copy was also out of date, which had seven quest tests failing before this work started. Worth a look.
  • The local config does not name a zone, so the server refuses to start without being told which one to load.

Verification

  • The full backend test suite passes — 29 of 29 packages.
  • Ten new tests covering the schema, run twice back-to-back to prove they leave no residue behind.
  • The chunk's stated goal is met and demonstrated: the schema builds onto an empty database and tears back down to a genuinely empty database, repeatedly.
  • The server was started for real, both with and without a database. With one configured, it created the schema and then reported zero errors and zero warnings, with all content loading exactly as before: 64 mobs, 86 skills, 15 factions, 4 quests, 777 props, 485 spawns, 5 campfires.
