Step 8a, Chunk 1c: the eight endpoints

Point-in-time summary · 1 August 2026 · branch accounts-8a

This is a human-facing snapshot, not a maintained document. The authoritative sources are docs/plan-accounts-frontend.md §3 and §3a (the endpoints and the wire contract) and §10a (the full chunk ledger), plus docs/plan-accounts-implementation.md §5b (the exact player-facing wordings) and §7b (transport and session security). Where this document and those disagree, they win.

In one sentence

Chunk 1b built every part a login needs but left them unreachable; this chunk connects them to the web, so aura now has working accounts — you can create a character with no signup at all, come back to it later, sign up without losing anything, log in, log out everywhere at once, and delete a character.

There is still nothing to click. The screens are chunk 2. What exists is the machinery behind them, exercised by tests and by hand over HTTP.

The eight endpoints

What a player is doing What happens
Creating their first character No signup, no form beyond a name. An account is minted behind them and its secret is handed to the browser once, to be kept in local storage. Account, credentials and character are written together or not at all.
Coming back later The browser presents that secret and gets their characters back.
Creating a second or third character The server picks the lowest free slot and refuses beyond the configured limit (three). Character names are unique across the whole game, case-insensitively.
Deleting a character The row is kept as history but marked deleted, and the name is released for anyone to use immediately. Refused while that character is in the world.
Choosing a character to play Ownership is proven here, and the server issues a one-time 30-second pass tied to that one character. The game connection presents only that pass.
Signing up A username and password are added to the account they have already been playing on, so signing up costs no progress. That is the whole point of the design.
Logging in / logging out Login sets a session cookie the browser cannot read. Logout does not merely clear that cookie — it cancels every session for the account, including a copy of the token taken off the machine.
Staying logged in while playing The client quietly renews its session on a timer, so a session never expires mid-fight. Renewal is refused once the account has logged out, been erased, or had its sessions cancelled — otherwise "quiet renewal" would mean "a stolen session lasts forever".

Two decisions worth knowing about

What a character may be called

Chunk 1b deliberately left this open rather than inventing a rule. It is now decided: letters (in any alphabet) and digits, joined by single spaces, apostrophes, hyphens or underscores, starting and ending on a letter or digit.

So Barney Rubble, M'reth, Zoë and Grimm-Ash are fine; Barney  Rubble (two spaces), -Bob-, emoji, and the stacked-accent "zalgo" text that turns a name into a smear are not.

The deciding argument was that the game's own name suggester proposes Barney Rubble — a stricter rule would have aura suggesting names it then refuses.

Two old, deliberate holes were closed

Two settings had been correct for years and stopped being correct the moment a login cookie existed:

  • Any website could open a game connection. Harmless while there was nothing to steal; once a browser carries a session, another site could have opened a connection and the browser would have attached your session to it.
  • The existing web endpoints advertised themselves as open to everyone. Correct for the two public catalogues of game content, and impossible to reuse for anything carrying a login — browsers refuse that combination outright.

Both now consult one shared list of permitted sites, built once when the server starts. A request from anywhere else is refused rather than quietly served, and the session cookie ships with the three protective flags in the same change — so no part of the protection rests on any other part.

How it was checked

Beyond the ordinary tests: twelve deliberate acts of sabotage, each breaking one important rule to confirm a test actually notices. Eleven were caught. Examples: making logout clear the cookie without really cancelling sessions; letting an unknown website through; making the "you are already logged in" rule apply per character instead of per account (which would have let one player run all three of their characters at once); and removing the check that makes a wrong password and an unknown username take the same amount of time — because if they do not, the identical error messages protect nothing against anyone with a stopwatch.

The twelfth survivor was not a missing test but a wrong comment: a guard the code claimed was protecting something turned out to be an optimisation, with the real protection one layer below it. Both comments were corrected.

The endpoints were also driven by hand against a running server — 25 checks, all passing — and the connection-origin rule was confirmed against the live game socket.

What is deliberately not here

  • Any screen. Chunk 2 builds character-select, the login and register forms, and the delete confirmation.
  • Entering the world as a chosen character. Chunk 3 connects the one-time pass to the game.
  • Saving progress. Chunk 4. Until then the account persists and the progress does not, which is no worse than today but will look broken to anyone testing it.
  • Logging out throwing you out of the world. It cancels your sessions, but disconnecting a live game connection needs machinery that arrives in chunk 3.
  • Password recovery. Its own plan, last, because it is the only part that needs the ability to send email — which aura does not have. Until then a forgotten password cannot be recovered, and the sign-up form will say so.

One thing to watch

The session cookie is marked as requiring a secure connection, always — including during local development, where browsers make a documented exception for localhost. That exception could not be confirmed here because there is no browser installed on this machine to test with, and two non-browser tools correctly refused to co-operate. It is the first thing chunk 2 should check in a real browser. If it does not hold, the fix is to serve the development client differently, never to remove the flag.
